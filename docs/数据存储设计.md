# 曙光英雄梯度 · 数据存储设计（v2 提案）

> 状态：**已选定 B（SQLite + JSON 快照）并落地**。
> 当前仅保留 `2026-10-19` 实验期作为数据库第一条数据；旧 6 期已封存到 `archive/legacy/`。
> 数据源：`曙光英雄_大神榜_全英雄_20261025.xlsx` + `曙光英雄_2026-10-19.json`。

## 实施状态（2026-10-25）

- 事实源：`data/tierlist.db`（`bun:sqlite`，WAL），表 `heroes / periods / hero_stats / rank_power`。
- 快照：`data/snapshots/2026-10-19/{period.json,power.json,players.json.gz}`，可重建数据库。
- 导入：`tools/merge_experimental.py` 合并 XLSX + JSON；`bun tools/db-setup.mjs --force` 写入 SQLite。
- 页面：`GET /api/periods/2026-10-19` 返回 103 英雄 + 每人 `power` 数组；算法 v4（头部均值 + 全榜均值）在 `js/algorithm.js`。
- 旧「国9」口径已取消：数据库中的 `power_top9` 等历史派生列保留用于兼容，不参与 v4 计算与页面展示。
- 旧数据：`archive/legacy/` 6 期不载入、不参与梯度。
- 选 B 的理由：玩家明细全存时单期 JSON 约 866 KB，周更一年约 45 MB；SQLite 单期约 0.5 MB、查询/历史/事务更合适。
- 下文第 4 节的「v2 分层 JSON」保留为对比方案，不再是当前实现。

## 2. 体积测算：一期一个 JSON 真的撑不住吗？

实测同一份数据的不同存法：

| 存法 | 单期大小 | 52 期/年 | 说明 |
|---|---:|---:|---|
| 只存战力分布（紧凑 JSON） | ~47–58 KB | ~3 MB | 算法所需的最小集 |
| v2 热数据（统计 + 分布 + 元数据） | ~58 KB 紧凑 | ~3.5 MB | 推荐的热文件量级 |
| 全量玩家明细（JSON 紧凑） | ~866 KB | ~45 MB | 昵称/UID 才是膨胀源 |
| 全量玩家明细（gzip） | ~196 KB | ~10 MB | 冷归档可接受 |
| SQLite（含玩家明细，原型实测） | ~500 KB | ~26 MB | 单文件，查询友好 |

> **核心判断**：一期一个「热 JSON」并不大。问题不是“一期一个文件”，而是“把 9,167 行玩家明细和算法要的分布混在一个文件里”。
> 只要把热数据（分布/统计）与冷数据（玩家明细）拆开，文件方案再撑 5–10 年也没问题。
> 真正需要数据库的临界点是：**日级采集、多地区/多服、按玩家检索、复杂跨期查询**。

## 3. 方案对比

### A. v2 分层 JSON（推荐，当前规模）

```
data/
  periods/
    2026-10-19/
      period.json      # 元数据 + 103 行统计/派生指标（编辑器读写）
      power.json       # 英雄 → [榜1..榜N] 战力数组（只读，导入生成）
  players/
    2026-10-19.json.gz # 可选冷归档：9,167 行玩家明细
  index.json           # 可选：期数索引（服务端也可扫描生成）
```

优点：
- 零依赖、可 git diff、可手工查看/修复；
- 主榜只需要 `period.json`（约 15 KB），英雄详情才按需读 `power.json`；
- 编辑器只编辑统计行，不会被 100 个数字的数组撑爆；
- 与现有 bun 静态服务器、SSE、编辑器模式最接近。

缺点：
- 跨期历史查询需要服务端聚合（不能纯静态）；
- 文件数随期数增长（每期 2 个热文件，年 104 个）；
- 写入需要「临时目录 + rename」保证一期两份文件一致。

### B. SQLite + JSON 快照（数据量再上一个台阶时）

```
data/tierlist.db          # 运行时唯一事实源（bun:sqlite，零依赖）
data/snapshots/<date>/    # 每次写入后自动导出 period.json + power.json，供 git/备份
```

表结构（原型已验证，9,167 行插入 0.02s，单期 DB ~500 KB）：

```sql
PRAGMA journal_mode = WAL;

CREATE TABLE heroes (
  id INTEGER PRIMARY KEY,
  name TEXT UNIQUE NOT NULL,
  profession TEXT,
  aliases TEXT,              -- JSON 数组
  active INTEGER DEFAULT 1
);

CREATE TABLE periods (
  id INTEGER PRIMARY KEY,
  date TEXT UNIQUE NOT NULL, -- 周期起始日 YYYY-MM-DD
  captured_at TEXT,
  source TEXT,
  source_hash TEXT
);

CREATE TABLE hero_stats (
  period_id INTEGER NOT NULL REFERENCES periods(id) ON DELETE CASCADE,
  hero_id INTEGER NOT NULL REFERENCES heroes(id),
  appearance_rank INTEGER,
  win_rate REAL,             -- 0..1
  rank_count INTEGER,
  PRIMARY KEY (period_id, hero_id)
);

CREATE TABLE rank_power (
  period_id INTEGER NOT NULL REFERENCES periods(id) ON DELETE CASCADE,
  hero_id INTEGER NOT NULL REFERENCES heroes(id),
  rank INTEGER NOT NULL,
  power INTEGER NOT NULL,
  player TEXT,               -- 可选
  uid TEXT,                  -- 可选
  PRIMARY KEY (period_id, hero_id, rank)
) WITHOUT ROWID;

CREATE INDEX idx_rp_hero ON rank_power(hero_id, period_id, rank);
CREATE INDEX idx_hs_hero ON hero_stats(hero_id, period_id);
```

优点：
- 历史/趋势/按玩家检索都是 SQL；
- 一期 500 KB，5 年约 130 MB，完全可控；
- 事务写入，不会出现半期数据；
- bun 内置，无需 npm 依赖。

缺点：
- 二进制、不可 git diff（用快照补偿）；
- 前端需要改成 API 取数，编辑保存接口也要改；
- 迁移和回滚成本高于文件方案。

### C. 直接上 SQLite（不做文件）

适合确定要做「日级 + 多地区 + 玩家检索」的情况；否则会把简单问题复杂化。

## 4. 推荐方案：v2 分层 JSON（A），保留升级到 B 的缝

### 4.1 目录

```
data/
  periods/
    2026-10-19/
      period.json
      power.json
  players/
    2026-10-19.json.gz       # 可选，默认不进 git 或走 LFS
  index.json                 # 可选，服务端扫描生成
英雄介绍.json                 # 升级为英雄主数据（registry）
HeadIcon/ banner/ ...        # 资源不变
```

- 旧文件 `曙光英雄_YYYY-MM-DD.json` 保持不动，读取层同时支持 v1/v2。
- 新周期只写 `data/periods/<date>/`，不再往根目录丢大盘文件。

### 4.2 period.json（编辑器读写）

```json
{
  "schema": 2,
  "periodStart": "2026-10-19",
  "capturedAt": "2026-10-25T11:49:00+08:00",
  "source": {
    "file": "曙光英雄_大神榜_全英雄_20261025.xlsx",
    "rows": 9167,
    "heroCount": 103,
    "hash": "sha256:..."
  },
  "metricsVersion": 1,
  "heroes": [
    {
      "name": "范蠡",
      "appearanceRank": 1,
      "winRate": 0.4679,
      "rankCount": 100,
      "powerTop1": 6228,
      "powerTop9": 5327,
      "powerTop50": 3313,
      "powerTop100": 2561,
      "powerMedian": 3313
    }
  ]
}
```

约定：
- `winRate` 用 0..1 数值，不再存 `"46.79%"` 字符串（展示层格式化）。
- `rankCount` 是真实榜长；`powerTopN` 在 N > rankCount 时为 `null`，不补 0。
- `metricsVersion` 标记派生指标算法版本；原始分布在 `power.json`，随时可重算。
- 职业建议放主数据（见 4.4）；period 里可选保留快照，避免历史职业被改写。

### 4.3 power.json（只读，导入生成）

```json
{
  "schema": 2,
  "periodStart": "2026-10-19",
  "rankFrom": 1,
  "heroes": {
    "范蠡": [6228, 6105, 6059, 5999, 5758, 5667, 5456, 5404, 5327, 5224, "..."],
    "李文": [6307, 4753, 4637, "..."],
    "尉迟炎": ["..."]
  }
}
```

约定：
- 数组下标 0 = 榜 1；长度 = `rankCount`；只允许从 1 开始连续。
- 写入时校验：长度、严格不增、无 0/空值；不合法整期拒绝。
- 用紧凑格式（数组一行），避免 100 个数字各占一行；period.json 保持 2 空格美化。
- 主榜不加载此文件；详情页/算法需要分布时再取（服务端可按英雄切片）。

### 4.4 英雄主数据（registry）

把 `英雄介绍.json` 升级为唯一英雄表（或在 `data/heroes.json` 新建，二选一）：

```json
[
  {
    "name": "许褚",
    "aliases": ["许禇"],
    "职业": "战士",
    "常用分路": [],
    "擅长选手": [],
    "active": true
  },
  {
    "name": "张角",
    "aliases": [],
    "职业": "法师",
    "常用分路": [],
    "擅长选手": [],
    "active": true
  }
]
```

- 归一化：`许禇` 自动映射到 `许褚`；导入时用 alias 匹配。
- 张角需要补 `HeadIcon/张角.png`、`banner/张角.*`、介绍记录；否则页面降级。
- 职业只维护一份；period 可保留历史快照，但新数据以 registry 为准。

### 4.5 索引与查询

- 服务端扫描 `data/periods/*/period.json` 生成 `/api/periods`，无需手写 index。
- 可选生成 `data/index.json` 给外部脚本用（非事实源）。
- 历史趋势：`GET /api/heroes/:name/history` 由服务端读取各期 `period.json`（每期 ~15 KB，52 期 <1 MB），不要前端一次拉全部 `power.json`。
- 分布详情：`GET /api/periods/:date/power/:hero` 从 `power.json` 切片返回；服务端可缓存解析结果。

### 4.6 兼容旧数据

- v1（现有根目录文件）：数组、`winRate` 字符串、`国9战力` 标量，无分布。
- v2：上述目录结构。
- 读取层统一适配：
  - `combat` 优先用 `power` 派生指标；无 `power` 时回退 `国9战力`；
  - `winRate` 统一转 0..1；
  - 旧期在详情里标注“无分布数据”，不伪造曲线。
- 迁移不删除旧文件；可选择把旧文件复制进 `data/periods/` 加 `legacy: true`，但非必需。

### 4.7 导入流程（XLSX → v2）

离线脚本（Python + openpyxl，项目运行时仍零依赖）：

1. 读 `全英雄榜单`，校验 103 英雄、名次连续、战力不增；
2. 读当期 JSON 的 `appearanceRank`/`winRate`；
3. 按 registry alias 归一英雄名（许禇→许褚）；
4. 计算 `rankCount` 与 top1/top9/top50/top100/median；
5. 写 `period.json` + `power.json`（临时目录 → rename）；
6. 可选写 `players/<date>.json.gz`；
7. 输出校验报告（缺英雄、缺职业、短榜、异常值）。

### 4.8 写入与备份

- 一期两份热文件必须一起更新：先写 `data/periods/.tmp-<date>/`，再 rename 目录；或先写 `power.json` 再写 `period.json`（读取端以 `period.json` 为提交标记）。
- `period.json`/`power.json` 进 git（每期 ~58–70 KB，年 ~3.5 MB）。
- 玩家 gzip 可选进 git/LFS；原始 XLSX 建议放 `imports/` 并 gitignore（单期 363 KB）。
- 若将来上 SQLite：DB 不进 git，快照目录继续进 git，DB 可由快照重建。

## 5. 算法层要预留的存储需求

- **原始分布是事实源**：topN/中位数/AUC/集中度都应由 `power` 现算，不要只存一个总分。
- **榜长不一致**：27 个英雄不足 100；指标要么按可用名次截断，要么显式 `null`，不能把缺失当 0。
- **跨期可比**：每期独立归一化；存储保留原始战力，归一化放算法层（可换版本）。
- **算法版本**：`metricsVersion` + 代码版本；换算法时能重算历史，不需要改数据。
- **旧期回退**：无分布期用 `国9战力` 标量，详情标注数据不完整。

## 6. 迁移顺序（建议）

1. **定 registry**：补张角、许褚 alias、职业；确认 103 英雄名单。
2. **写 v2 导入脚本**：先只生成 2026-10-19，不动旧数据。
3. **服务端 v2 读取/扫描/API**：`/api/periods`、`/api/periods/:date`、`/api/heroes/:name/history`；继续兼容根目录 v1。
4. **前端适配**：主榜读 period.json，详情按需读 power；旧期回退。
5. **编辑器适配**：显示/编辑 period.json，power 只读摘要（榜首/榜长/topN）。
6. **验证**：103/103 匹配、27 个短榜正确、旧 6 期排名不变、新一期可算分、SSE 刷新。
7. **再决定是否迁移旧 6 期**（可保留 v1 不动）。

## 7. 什么时候改用 SQLite（B）

满足任意两条即可考虑：

- 采集频率到**日级**（365 期/年，文件数 730+）；
- 需要**多地区/多服**（期数 × 地区）；
- 需要按**玩家昵称/UID**检索、跨英雄统计；
- 需要在服务端做复杂聚合（分位数、版本对比、批量导出）；
- 多人/多端同时编辑。

以当前「周更 + 103 英雄 + 只算分布」的规模，A 方案足够；B 的方案已在上文给出，v2 JSON 可 1:1 导入 SQLite，不会返工。
